# 真实多人接入前就绪说明

## 已具备

- 山门、云庭、大殿三段空间和角色连续移动。
- 山门双扇门可在山门视角闭合，并在进入路线时开启。
- 本地角色状态：法号、颜色、位置、座位、当前仪式动作。
- 选座、离座、礼拜、合掌、实体木鱼敲击、108 珠念珠和静坐交互。
- 本地环境访客、法号标签与人数展示。
- 分区声音、渲染降载和场景诊断数据。

## 当前本地 Presence 的边界

`src/presence.js` 使用浏览器 `BroadcastChannel`：

- 只在同源、同一浏览器环境的标签页之间同步；
- 没有服务器房间，也不能跨设备或跨浏览器；
- 座位状态由每个客户端自行判断，不具备权威抢座仲裁；
- 4 秒心跳与 15 秒淘汰只是本地演示逻辑；
- 没有身份恢复、网络重连补帧、状态版本或冲突处理。

因此页面里的“24 人在线”和 17 名环境访客属于氛围层，不是线上真实在线数据。

## 下一阶段最小实现顺序

1. 定义房间与状态协议：`join`、`snapshot`、`move`、`action`、`claimSeat`、`releaseSeat`、`ping`、`leave`。
2. 建立 WebSocket 房间服务，服务端生成玩家 ID 并维护权威快照。
3. 将座位申请改为服务端原子仲裁，失败时返回明确占用者和新版本号。
4. 客户端增加插值、动作序号、心跳、指数退避重连和断线后的全量快照恢复。
5. 用两台设备验证加入、移动、同时抢座、掉线重连与离开回收。
6. 最后再把氛围人数替换为真实在线人数，并决定是否保留环境访客补位。

## 推荐架构

保持渲染层和房间层分离：

```text
TempleScene（本地移动、动画、相机）
        ↓ 本地状态 10 Hz
MultiplayerRoom（协议、重连、插值）
        ↓ WebSocket
Room Service（权威房间状态、限速校验、座位仲裁）
        ↓ 可选持久层
会话 / 房间配置 / 运营数据
```

- `TempleScene` 继续负责本地即时响应，不等待服务器才移动。
- 新建 `MultiplayerRoom`，保持当前 `PresenceRoom` 的 `subscribe`、`update`、`destroy` 接口，减少主页面改动。
- 服务端只维护影响其他人的状态：玩家身份、场景、位置、朝向、移动/坐姿、动作、座位和最后心跳；相机距离与个人视角不上传。
- 一个房间先限制 30～50 人。环境和尚可以作为客户端氛围角色，不占真实房间席位；真实在线人数必须来自服务端快照。

## 状态协议

客户端发送：

```json
{ "type": "join", "roomId": "node-07", "resumeToken": null, "profile": { "name": "云外旧梦", "color": 10187340 } }
{ "type": "move", "seq": 42, "view": "courtyard", "x": 1.24, "z": 13.8, "yaw": 3.14, "walking": true }
{ "type": "action", "seq": 43, "name": "gassho", "nonce": "..." }
{ "type": "claimSeat", "requestId": "...", "seat": 12 }
{ "type": "releaseSeat", "requestId": "..." }
{ "type": "ping", "clientTime": 1794700000000 }
```

服务端返回：

```json
{ "type": "snapshot", "version": 81, "selfId": "p_123", "players": [], "seats": [], "serverTime": 1794700000032 }
{ "type": "playerDelta", "version": 82, "player": { "id": "p_456", "x": 1.5, "z": 13.2, "yaw": 3.1, "walking": true } }
{ "type": "seatResult", "requestId": "...", "ok": true, "seat": 12, "version": 83 }
{ "type": "playerLeft", "version": 84, "id": "p_456" }
{ "type": "pong", "serverTime": 1794700000050 }
```

所有增量带递增 `version`，客户端发现跳号时请求全量 `snapshot`，避免漏包后状态永久错误。

## 移动同步

1. 本地玩家继续立即移动和播放动画，保持当前手感。
2. 客户端以 10 Hz 上传 `x/z/yaw/view/walking`，位置没有显著变化时不发送。
3. 服务端检查最大速度、可行走区域和场景边界，再以 10～15 Hz 广播。
4. 远端角色不直接跳到新坐标，保留约 120 ms 插值缓冲；短时丢包用最近速度外推，超过 500 ms 停止外推。
5. 相机模式、相机距离、鼠标位置属于个人状态，不进入多人协议。

## 权威座位仲裁

- 客户端点击空坐垫后先显示“正在确认”，发送 `claimSeat`，不立即宣布成功。
- 服务端在同一个房间状态事务中检查并写入座位占用；同一时刻只有一个请求能成功。
- 成功后广播座位版本，失败返回当前占用者，客户端恢复站立并提示选择其他坐垫。
- 连接断开进入 20～30 秒恢复期；恢复期内保留座位，超时后服务端释放。

## 断线恢复与身份

- 首次加入由服务端签发短期玩家 ID 和不可猜测的 `resumeToken`。
- WebSocket 断开后采用 1、2、4、8、15 秒指数退避，并显示“正在重连”，场景仍可本地浏览。
- 重连携带 `resumeToken`；成功后用服务端全量快照覆盖远端玩家和座位，本地未确认动作不重复提交。
- `requestId`、`seq` 和动作 `nonce` 用于幂等，防止重连造成重复入座或重复动作。

## 客户端改造点

1. `src/presence.js` 保留为本地开发适配器，新增 `src/multiplayer-room.js` 作为 WebSocket 生产适配器。
2. `TempleScene` 增加 `getLocalTransform()`，返回 `view/x/z/yaw/walking/action/seat`。
3. `syncPeers()` 改为给每个远端角色保存前后两帧网络状态，由渲染循环插值。
4. `onSeatSelected` 拆成“请求座位”和“服务端确认入座”两个阶段。
5. 页面人数改为服务端 `players.length`；环境和尚另行标记，不混入在线人数。

## 分阶段交付

| 阶段 | 内容 | 验收 |
|---|---|---|
| M1 | 协议与 WebSocket 房间、加入/离开/快照 | 两台设备能看见对方上线和离线 |
| M2 | 位置、朝向、场景和动作同步 | 两台设备连续行走、切换场景和做动作无明显跳动 |
| M3 | 服务端原子抢座、离座和断线保留 | 两人同时抢同一坐垫只能一人成功 |
| M4 | 重连、补快照、限速与监控 | 断网恢复后位置和座位一致，无重复角色 |
| M5 | 压测、真机性能和灰度 | 目标房间人数下延迟与帧率达标后再公开放量 |

## 真实多人验收门槛

- 同房间跨设备可见，加入/离开状态在 2 秒内一致。
- 远端移动在正常网络下无明显瞬移，动作只播放一次。
- 100 次双人同时抢座测试中不出现双占。
- 断网 10 秒内恢复时身份、位置、座位不丢失；恢复失败时能干净地重新加入。
- 服务端拒绝越界坐标、异常速度、无效座位和过频消息。
- 公开放量前补做此前暂缓的手机真机帧率与网络弱网测试。

## 进入真实多人前仍保留的非阻塞项

- 手机实机帧率测试按当前决定暂缓，但公开放量前必须补测。
